ackshually

Settle a board-game rules dispute mid-game. Ask about the rulebook PDF, get the ruling at once, and swipe through the highlighted evidence when someone pushes back.

1 · Product

The moment

Mid-game, someone asks "wait, can I do that?" and the table is waiting. Speed and trust beat depth. Anyone at the table may ask, and the phone often gets handed to the skeptic.

Principles

  1. Ruling first, proof on demand. The verdict shows immediately; the evidence is one swipe away.
  2. The source is the star. The rulebook page stays on screen; the app never hides what the rule actually says.
  3. Never confidently wrong. Every answer is labeled Stated, Inferred or Not covered. External sources are always labeled.
  4. Never block the table. No waiting to upload, prepare or confirm before asking.
  5. Neutral referee. Verdicts are plain and fair; personality lives in the name, labels and empty states.

In scope now

  • Rulebooks uploaded by the user. A game holds one or more: core books (always on) and optional add-ons (expansions, FAQs, errata) ticked for each game night (S13, M3).
  • Ask by typing or push-to-talk. Answers on screen, optional read-aloud.
  • Branches when the outcome depends on something unstated.
  • Conversation context per session; sessions saved per game, on device.
  • Web fallback (BGG / Reddit) when the rulebook doesn't settle it.
  • 👍/👎 per answer; export a game's data as JSON.

Not now

  • Asking clarifying questions.
  • Curated rulebook library.
  • Remembering past rulings as house rules.
  • Server, other users, Android, iCloud sync.

2 · Screens

Milestone in the tag. Gestures in bold. Blue marks on the mockups show the gesture being described.

S1 · My Games M2 · sessions in M3

The app opens here. A standard list of imported rulebooks, most recently used first: cover (the PDF's first page), game name, "Opened 2 days ago". Settings, Edit and ＋ Add Rulebooks are in the toolbar.

  • Tap a game → viewer (pushed; Back returns to the list). Coming back to the same game keeps its answer. A game with optional rulebooks asks what you play with first (S13).
  • ＋ → iOS file picker, several PDFs at once (on a Mac, PDFs can also be dropped on the list) → the copies go to the review sheet (S14), where the app suggests which game each belongs to and the user confirms. One PDF takes the same path.
  • A game with several rulebooks says so under its name ("7 rulebooks"); the cover is its first core book.
  • Swipe left → Delete (removes the game and its copies). A game with several rulebooks asks first: "Delete Root and its 7 rulebooks?". Export comes with S12 sessions.
  • Edit → select several games → Delete (with the same question). Settings → Developer → Remove All Games empties My Games after a confirmation.
  • No games yet: "Add a Rulebook" or "Try the Sample".
  • iPad / wide: the same stack; the viewer keeps its answer column.

S2 · New game, preparing M2 · OCR in M3

  • The PDF is readable and askable immediately.
  • A thin progress line appears only if pages need OCR (scans, outlined text), then disappears.
  • Until a page is prepared, highlights on it fall back to showing the whole page.

S3 · Asking M2

  • Type and send: always available, for private questions.
  • Hold 🎙: live transcript, release to send, slide left to cancel.
  • Tap 🎙: dictation; review and edit before sending.
  • The PDF can be browsed freely (pinch, scroll) at any time.

S4 · Answer arriving M2

The sheet rises as soon as the first words arrive and fills in this order:

  1. Restated question ("3 energy + a Battery, at end of turn"). If it's wrong, Stop and rephrase without waiting.
  2. Verdict + proof line (placeholder text until they arrive).
  3. Step 1: the PDF jumps to the page, zooms and highlights. Later steps keep loading.

Between send and the first token the ask field shows Reading the rulebook… with the question and Stop; the sheet rises on the first token.

The sheet holds still while the answer streams. It rises straight to its medium size: a placeholder step card (as tall as a full card) and the follow-up row (disabled until the answer is done) hold their places from the first token, so content fills in place. When the answer completes, the sheet settles once, animated, to the finished content: it can grow for late content (branch rows come last), or shrink as the cards fit their text again. It never moves while streaming.

S5 · The answer sheet M2

Two layers, no Back/Continue buttons:

A system sheet with three detents (collapsed, medium, large); the PDF stays usable under it up to medium. No Back/Continue buttons:

  • Answer header, fixed while stepping: text hierarchy, no chips. Bold verdict (one short sentence; at most 3 lines on the sheet, the full text when expanded), then one secondary proof line (checkmark.seal Stated in the rules · p.12, p.14). Close (or Stop while streaming) top-right.
  • Step cards: a horizontal shelf of system cards; the next card peeks from the edge, which signals "swipe". Caption = step title + page, then one or two sentences. All cards share one height, the tallest card's content up to 5 lines of text; longer text truncates with More, which opens the expanded answer at that step. Text never runs outside its card at any Dynamic Type size. Page dots below. While an answer streams, the loading card keeps the shelf at a full card's height so nothing below it moves; once the answer is complete, the cards fit their content.
  • Follow-up + 👍/👎 row under the cards (follow-up field, thumbs), once the answer is complete. There is no closing "Result" card: it only repeated the verdict.
  • Branch rows under that (Without a Battery … Discard all 3 ›), grouped like Settings.

S6 · Stepping M2

  • Swipe left / tap the right peek → next step. The PDF follows the card: page turn, zoom, highlight.
  • Swipe right / tap the left peek → previous step.
  • Last card = the last step, which applies the rules to the player's situation (never a restated verdict).
  • Spotlight: the cited passage is outlined in the brick tint and the rest of the page is dimmed, so it can't be confused with the rulebook's own frames or lost on a cream page.
  • A step can cite several passages (pager "Quote 1 of 2 ›" on the PDF) or a figure (same spotlight around the box; if no usable box, the whole page + "see the diagram, lower half"). When only part of a quote is found, that part is spotlit with a note Part of the passage highlighted. When a quote isn't found, the whole page shows with a note Passage not found · showing the whole page: no spotlight is never silent. The pager and the note share a row when both fit, otherwise the pager sits above the note; the evidence is centered below them.
  • ⋯ → Answer Details lists every cited passage (page, quote, matched / matched in N pieces / partly matched · coverage / not matched and why) with Copy JSON (raw answer + match results), to investigate a missing highlight.

S7 · Show the skeptic M2

  • Drag the sheet down → page near full-screen, the collapsed detent keeps the verdict + proof line (with pages) at the bottom.
  • Drag up to restore.

S8 · Inspect freely M2

  • Pinch / pan the PDF at any time to read the surrounding qualifications. Tapping the PDF never changes steps.
  • Double-tap: after a pinch/pan, back to the highlight; otherwise evidence zoom ↔ full page. No floating button: a new card or quote also re-centers.

S9 · Full answer M2

  • Drag the sheet up (large detent) → restated question, header, then the step cards unfold in place into grouped Steps rows (tap one to drop back to its card), then the same follow-up + thumbs row as medium, If…, Assumes. Nothing shows twice. A branch whose verdict is a sentence puts it under the condition.
  • Tap a branch row → the header shows that branch's verdict and the step cards switch to the branch's own steps (branches[].steps); a "Main Answer" row returns.
  • Wide screens (iPad, Mac, phone landscape): the same content in a trailing column beside the PDF; a toolbar button shows/hides it.

Screenshots of the built app: m2-screenshots/restyle/ (they supersede the mockups' visual treatment).

S10 · Not covered → web M4

  • Triggered when the rulebook answer is Inferred or Not covered. The rulebook part shows first; a "Searching BGG & Reddit…" card fills in after.
  • Web findings are bordered step cards, never PDF highlights: site, date, author role (designer / publisher / community), quote, link.
  • If a source disagrees, the rulebook verdict stays in the header and the card says ⚠ Designer disagrees (strong) or ⚠ Community disagrees (soft).

S11 · Feedback M3

  • 👍 is saved silently.
  • 👎 → one-tap reason (wrong verdict, missed exception, wrong highlight, wrong page, too slow, other), optional step, optional note.
  • ⋯ → Export game: one JSON with all sessions, questions, full model outputs, timings, tokens and ratings.

S12 · Sessions M3

  • ⋯ → Sessions: past questions per game, grouped by night. Tap → reopens that answer.
  • New = new game night; clears conversation context.

Read-aloud M4

No screen. Off by default, toggled in ⋯. Speaks the restated question and verdict only. Any tap stops it.

S13 · Playing with M3

A game is a set of rulebooks: core books are always on, add-ons (expansions, FAQs, errata) are ticked per game night. Answers only use what is ticked.

  • Shows every time a game with add-ons is opened from My Games (the table changes from night to night). Games with only core books skip it.
  • Core books are listed, checked and can't be unticked. Tap an add-on to tick or untick it. The ticks start from the last time this game was played, so Play is usually one tap.
  • In the viewer the title becomes a button ("Root · Riverfolk, Rootbotics"); tap → the same list. A change applies from the next question; the answer on screen stays.
  • Swipe left on a book → Remove (from this game and the device); removing a game's only book offers to delete the game. ＋ Add Rulebooks at the bottom opens S14 with this game suggested. Long-press → Make Core / Make Add-on, Rename.
  • Every session records which books it was played with (S12).
  • Answers: the ticked books are sent as one document, each book's pages in a row, with a table of contents (book, kind, page range) and an order of authority: errata and FAQs over a rules reference, a rules reference over a learning guide. Unticked add-ons are named as not in play, because a core reference can cover them too (the Law of Root has sections for the expansion factions). Evidence pages come back as book + page ("Riverfolk p.4", on cards, the proof line, the quote pager and Answer Details); the viewer shows the ticked books one after another, with a book switcher.
  • Not in play: a question about an unticked add-on's content is still answered when a ticked book covers it (the Law of Root does), with the assumption that it is in play; otherwise it is not covered and names the add-on.
  • Size: a set over ~22 MB of PDF (the API takes 32 MB per request, base64 adds a third) is sent as an excerpt of the best-matching pages, never whole, and with no full-document retry. Joined PDFs are kept on the device, so the 1-hour prompt cache keeps hitting across launches (PDFKit writes different bytes on every join).
  • A change of books starts a new conversation: earlier turns cite pages of the old document. ＋ never replaces a file another book uses (a taken name gets a number): a file belongs to one game.

S14 · Adding rulebooks M3

A game often comes as several PDFs (Root: a rules reference, a learning guide, five add-on booklets). ＋ takes them all at once; the app suggests the games, the user confirms.

  • ＋ in My Games → file picker with several selection. On a Mac (Designed for iPad), PDFs can be dropped on My Games. One PDF goes the same way.
  • The sheet Add N Rulebooks opens at once and always shows, even when the suggestion is sure. Files start under Sorting… and move into game groups as the suggestion arrives (a second or two).
  • Group header: the game's name (tap to rename) and New game or In My Games. Row: cover thumbnail, title (tap to rename), a Core / Add-on menu.
  • Drag a row to another group, or long-press → Move to… an existing game or a new one. A file the suggestion flags as not a rulebook (a score sheet, a player aid) starts under Skipped, with the reason; Move to… brings it back.
  • Nothing is saved until Add. Cancel removes the copies. Opened from ＋ in Playing with (S13), the sheet suggests that game.
  • After Add: one new game → it opens (with its Playing with list first if it has add-ons, S13); otherwise back to My Games (from Playing with: back to that list).
  • Suggestions: one Claude Haiku call per batch, through the ackshually server only (the bundled token or the developer token override). Per file it sends the file name, the PDF's title, the page count and the text of the first 2 pages (≤1,500 characters), plus the names of the games and books already in My Games; never the PDF. It returns, per file, a game (existing or new), core or add-on, a clean title, a short reason and a not-a-rulebook flag. The rules reference and the main learning guide are core; expansions, FAQs, errata, variants and walkthroughs are add-ons.
  • No suggestion (no server credential, only a developer API key, offline, or an error): every file is its own new game, core, titled from the PDF title or the file name, and a quiet note says "Sort these yourself". The app doesn't guess from file names.

3 · Visual style

Direction (2026-11-21): native iOS, warm. Use standard components and let the warm palette tint them. Reference: design/native-ios.html. It overrides the visual treatment of the S-mockups above (which still define layout and interactions) until they are redrawn.

  • System components first: system sheet with detents, navigation bar with a standard ⋯ menu, an answer column on wide screens, grouped rows (like Settings), SF Symbols, native page/scroll behavior, Liquid Glass for controls floating over the PDF (ask field, passage pager, close/stop). No custom pills, outlined chips or boxed web-style cards.
  • Text hierarchy instead of decoration: bold verdict (title3), then one secondary line of proof ("checkmark.seal Stated in the rules · p.3, p.4"; inferred: exclamationmark.triangle, not covered: questionmark.circle). The restated question shows only while waiting and in the expanded view. "Demo answer" is a footnote in the expanded view and a note in the ⋯ menu, never on the verdict.
  • Step cards keep the peek, styled as system cards (App Store / Music shelves): rounded, no borders or shadows; caption = step title + page.
  • Branches, steps, feedback are standard rows with chevrons / values.
  • Warm, but restrained: brick red as the app tint, warm sheet and grouped backgrounds, a clearly darker warm navigation bar with a hairline under it (and between the PDF and the answer column), so bar, PDF and answer panel read as three surfaces. Evidence is a spotlight (dimmed page, brick outline), not a highlighter. Not plain white; not beige everywhere.

4 · Answer contract

What the model returns. Field order is streaming order: it is what lets S4 show the restated question, then the verdict, then step 1. Branches and assumptions come after the main steps so they never delay step 1.

{
  "restated_question": "You have 3 energy and a Battery at end of turn.",
  "verdict": "Keep 2 energy, discard 1.",
  "confidence": "stated | inferred | not_covered",
  "steps": [
    {
      "title": "General rule",
      "text": "Unused energy is discarded at end of turn.",
      "evidence": [
        { "page": 12, "quote": "discard all unused energy", "box": null }
      ]
    }
  ],
  "branches": [{
    "condition": "Without a Battery",
    "verdict": "Discard all 3.",
    "steps": [{ "title": "General rule", "text": "…", "evidence": [ … ] }]
  }],
  "assumptions": ["The Battery is already in play."],
  "needs_web": false
}

Lengths: the verdict is one sentence of at most ~12 words (no reasons or pages; those are the steps); each step is one or two short sentences; the last step applies the rules to the player's situation and never restates the verdict, and no step is titled "Result". The app also caps the verdict at 3 lines and card text at 5 lines (More).

page is a page of the document that was sent. For a game with several rulebooks (S13) that is the ticked books one after another; the app maps it back to a book and its own page number. The JSON stays the same.

box is {x, y, w, h} normalized 0–1, used for figures. title (2–4 words) is the card caption. A branch carries its own steps (usually one) so the cards can switch to it (S9). Both are required by the structured-output schema and optional when decoding, so older answers still load (no title → "Step N"; a branch without steps → one card).

Placing a highlight, in order

  1. Match quote to the page's words as a continuous passage (PDF text layer, or OCR words for scanned/outlined pages) → word-level highlight. Geometry: PDFKit's per-character boxes are indexed without the line breaks in the page text (plus some drift), so boxes are located by checking which index mapping makes box widths match the characters' widths; when none fits, show the whole page rather than a box in the wrong place (2026-11-21, Azul).
  2. Layout-tolerant match (fragments): multi-column pages and text over art interleave the text layer's lines (main column, sidebars, boxes). Cover the quote with long fragments (≥ 20 normalized characters and ≥ 4 words each, whole words, small gaps bridged) that each match the page text, with unrelated text allowed between them; they must cover ≥ 85% of the quote and, once located, form one block on the page: each fragment continues the previous one on the same line or the next lines (same column, or a wrap back to the line start), and the block covers ≤ 20% of the page. Scattered fragments are rejected. Claimed page, then its neighbours. Geometry: when no single index mapping fits a passage (a ligature, glyphs stored out of order), word chunks are located piecewise and grown from the best-correlating one only while each chunk correlates and continues the previous one; text drawn under 4 pt is never boxed. (2026-11-22, Root p.15.)
  3. Partial match: if only part of the quote is found, but one fragment is long (≥ 30 characters, ≥ 6 words) and passes the same block check, spotlight that part and say so (Part of the passage highlighted; Answer Details shows the coverage). Claimed page only. Better a partial spotlight than the whole page.
  4. Vision OCR (M3): if that fails, OCR the page (visual reading order) and retry. Captions over artwork stay unmatched until then.
  5. Repair call (background, cheap model): "this quote wasn't found on p.N; here is the page text; return the exact passage." The highlight appears a moment later.
  6. Otherwise draw box if it passes sanity checks.
  7. Otherwise show the whole page and log a miss.

Every match records its kind (continuous · fragments · partial), coverage, the fragments' rects and a block score; Answer Details, the debug log and bench show it. Bench: bench match-set is a question-free regression set on the real rulebooks, bench rescore re-matches a recorded run offline.

Evidence mode: quotes written by the model (json). M1 compared it with Claude's native PDF citations, which gave lower accuracy, fewer clean highlights and no figure boxes.

5 · Architecture

Living diagram of the app's parts and dependencies: architecture whiteboard (private Claude whiteboard; ask the owner for access). Keep it in sync with the code; see CLAUDE.md.

Core/    Swift package, no UI (macOS + iOS)
         models · library index · RulebookSorter (S14 suggestions, Haiku) · AnswerProvider protocol + ClaudeProvider (+ PageSelectingProvider: page-selection experiment) · streaming field parser
         quote matcher (fuzzy) · box checks · [M3] Vision OCR prep · [M4] web fallback
evals/   bench CLI on Core: question sets, runs, kept results
App/     [M2] SwiftUI app: PDFKit viewer, answer sheet; project generated from App/project.yml (XcodeGen)
Server/  Node 24 service at ackshually.badyass.xyz: holds the API key, checks and forwards answer requests
  • The app and the evals share Core, so benchmark numbers reflect the app.
  • Whole PDF + question + conversation in one streamed request; the PDF is prompt-cached with a 1-hour TTL (mid-game questions are often 5–60 min apart; a cache write costs 2× input instead of 1.25×, which pays off from the third question).
  • Data model: Game → [Rulebook] (each core or add-on, in the user's order, each add-on remembering whether it was ticked last time) is in the library index (LibraryIndex v2 in Core; a v1 index loads as one core book per game). Game → [Session] → [Answer] with each session's ticked books comes with S12. The answer request carries the ticked books (RulebookContents: table of contents, page map, add-ons not in play); RulebookJoiner joins them into one PDF, so page selection, the excerpt → original page remapping and caching work unchanged, and RulebookContents.reference(for:) maps an evidence page back to (book, page). Everything on device. In memory the app keeps one viewer session per recently opened game; a change of books is staged on it and applies from its next question.
  • App structure: each opened game gets a ViewerModel, a thin coordinator over AnswerSession (asking, streaming, follow-ups, failures), CardNavigator (cards, branches, quote pager), HighlightStore (quote → highlight, off the main thread) and PDFFocusModel; it owns the one rule for when the answer sheet shows. LibraryModel keeps the last few games' sessions. Outside services (credentials, settings, library files, answer providers) are small protocols bundled as AppDependencies, created once in the app and injected, so the answer logic is unit-tested with a scripted provider, and screens are checked in-process (layout assertions on hosted views, snapshot images from the preview fixtures); UI tests only cover what needs the running app (see m2-notes).
  • API key: only on the server (Server/) and in ANTHROPIC_API_KEY for the evals; never on the phone. The app sends the same streamed request Core builds today to ackshually.badyass.xyz/v1/messages with an app token; the server checks it against an allowlist of Core's two request shapes (answers: the answer models, max_tokens, no tools; rulebook sorting, S14: Haiku only, a small max_tokens, text only, no document), adds the key, pipes the stream back unchanged, and logs tokens and cost per request with daily caps. Page selection stays on the device (it uses PDFKit), so the server needs no rulebooks. The app token is built into the app (build setting from the git-ignored App/Config/Secrets.xcconfig → Info.plist → ServerConfig), so the default experience needs nothing entered; Settings says "Answers by ackshually server". Credential order: bundled token → server; else a developer token override (Settings → Developer, Keychain) → server; else the developer's own API key → Anthropic directly; else Settings opens with the question kept. A bundled token can be extracted from the binary: fine for our devices and TestFlight; revoking it means rotating it on the server and rebuilding. App Attest before a public release. Server errors arrive in Anthropic's shape: 401 → "check it in Settings" with an Open Settings button, 429 → "try again in N seconds" (per-minute limit, retry-after) or "try again tomorrow" (daily cap, no retry-after). ⋯ → Answer Details shows which route answered.
  • Step carousel: horizontal ScrollView + .scrollTargetBehavior(.viewAligned), side margins for the peek, .scrollPosition(id:) drives the PDF. Fallback: TabView(.page).
  • Figures: v1 uses the model-proposed box. If boxes score badly, use Vision-detected candidate regions and let the model pick one.

M1 tests five assumptions

  1. One call with the full PDF answers correctly with usable evidence (target ≥90%).
  2. Verdict + step 1 arrive fast when streamed (median ≤5 s, 90% ≤10 s).
  3. Quotes land on the right words (≥90% of highlights).
  4. Model-proposed boxes land roughly right on figures (Azul).
  5. Cost per question is tolerable, and caching makes follow-ups cheap.

Result: 1 ✅ (Sonnet 27/28, Opus 28/28) · 2 ❌ (step 1 median 6.0 s; the PDF size sets a ~4–5 s floor) · 3 ✅ (94–97%; misses were our text extraction) · 4 ⚠️ barely exercised · 5 ✅ (Sonnet ~$0.28 for 20 questions). See m1-report.md and eval results.

Speed experiment (alongside M2): select the relevant pages locally and send only those; success = step 1 median ≤5 s with no accuracy loss.
