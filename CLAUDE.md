# Working in this repo

- The product spec is `docs/spec.html` (HTML, not Markdown). Screen mockups come from `docs/design/screens.js`; insert one with `<div class="shot" data-screen="sN"></div>`. When a decision changes, add a row to the spec's decision log (§7) and update the sections it affects, so text and mockups never disagree.
- The answer engine lives in `Core/`; the app and the evals use the same code path. Keep `Core` UI-free and building for both macOS and iOS.
- Evals: `evals/` (`bench` CLI). Every run writes to git-ignored `evals/out/`. Copy runs that inform a decision to `evals/results/<date>-<label>/` and add a row to `evals/results/README.md`. Expected answers in question sets must be verified against the actual PDFs (`assets/rulebooks/`), with the page and an exact quote.
- The API key comes from `ANTHROPIC_API_KEY`; never write it to a file in the repo.
- Rulebook PDFs are copyrighted and git-ignored. Don't commit them or long excerpts.
- Default answer config (from M1): `claude-sonnet-5-5`, `json` evidence mode, effort `low`.
- iOS app (`App/`): small, modular SwiftUI components, one concept per file, grouped by feature. Leaf views take plain values + action closures (no network, Keychain or global state); orchestration lives in a few injected `@Observable` models. All colors, radii, spacing and type styles come from one Theme file (spec §3). Every component has `#Preview`s covering its states, built from shared fixtures so screens can be iterated on without an API key.
- No static layout in the app: theme injected via the SwiftUI Environment with semantic tokens; Dynamic Type text styles and `@ScaledMetric` for sizes that should scale; sizes relative to the container (`containerRelativeFrame`, sheet detents), never fixed frames; adapt to size classes/orientation in one container view (`ViewThatFits`/`AnyLayout`). Preview on small and large iPhones, landscape, iPad, largest text size and dark mode.
- SwiftUI skills are vendored in `.claude/skills/`: use `swiftui-expert-skill` when writing or refactoring app code, and run `swiftui-pro` as a review pass before opening an app PR. Project rules here win where they differ (e.g. we do want Liquid Glass/system materials, per spec §3).
- Toolchain: Xcode 27.2 / Swift 6.4 on macOS 27, XcodeGen 2.48+ (`brew install xcodegen`). Target the current iOS SDK.
- The Xcode project is generated and git-ignored: `App/project.yml` is the source of truth (targets, scheme, test plans). Run `App/bootstrap.sh` after cloning, after pulling and after changing `project.yml`; never edit `Ackshually.xcodeproj` by hand.
- App dependencies: models get `AppDependencies` (credentials, settings, library storage, answer providers) by initialiser; glue views read it from the environment. Only the live implementations (`App/Sources/Services/Dependencies/`) and `LaunchOptions` touch the Keychain, `UserDefaults`, `Library` or `ServerConfig`. Previews and unit tests use the in-memory ones (`Preview Content/InMemoryDependencies.swift`).
- App testing, three layers, all in-process except the last: (1) answer, card, highlight, sheet-rule and library logic is unit-tested in `App/Tests` against a scripted provider (milliseconds); (2) layout is asserted in-process (`App/Tests/Layout`): `HostedView` puts a view in its own window at a fixed size, text size and appearance, and reads element frames by accessibility identifier (margins, what each detent shows, card text inside cards, verdict cap, note vs. pager, landscape column, Settings, empty states); (3) looks are snapshot-tested (`App/Tests/Snapshots`, swift-snapshot-testing) from the same fixtures as the `#Preview`s, a short hand-picked list. `App/UITests` keeps only what needs the running app (8 tests): sheet detents and drags, card swipes, the sheet holding still while streaming, PDF pan/double-tap and spotlight, navigation My Games → viewer → back, Settings, the server stub route, and one tour of every screen for the console check. Every bug found by hand gets an automated test before the fix is merged, in the cheapest layer that shows it (a UI test only when only the running app shows it). Launch arguments for UI tests are in `App/Sources/App/LaunchOptions.swift` (`-noKey YES` ignores every credential, `-demoPace 0` streams the demo answer instantly). Several agents may test at once: create your own simulator (`xcrun simctl create "iPhone 18 Pro (<task>)" com.apple.CoreSimulator.SimDeviceType.iPhone-18-Pro com.apple.CoreSimulator.SimRuntime.iOS-27-2`), pass `-destination 'id=<udid>'`, run `xcodebuild` under `taskpolicy -b`, never with parallel testing (it clones the simulator per worker), and delete the simulator when done.
- Console check: the app's console is part of the tests. `App/TestPlans/console-check.sh <udid> [xcodebuild args]` runs Smoke on your simulator, reads the app's unified log, and fails on anything that isn't in `App/TestPlans/console-allowlist.txt` (it prints the offending lines). `--since "<time>"` checks a run you did by hand; `--file console.txt` checks a console copied from Xcode.
  - App PRs pass the console check.
  - A console message the owner reports is a bug: first a check that fails on it (the console check, or an in-process test using `ConsoleLog` from `App/Tests/Support`), then the fix.
  - New system noise goes into the ignore list deliberately: one regex per line with ` # ` and the reason, after checking it isn't ours (a bare app, a system process or the owner's log shows it too). Never add a message our code causes.
  - Debugging a SwiftUI message: `TEST_RUNNER_APP_AG_TRAP_CYCLES=1` (UI tests pass `APP_*` runner variables to the app without the prefix) crashes on an AttributeGraph cycle, so the crash report has the stack.
- Snapshots: reference images are recorded on iOS 27.2 (other runtimes skip them), at 2×, 8-bit, animations off. They may only show fixtures and the generated sample rulebook (Power Plant Rush), never a real rulebook page. A missing reference is recorded on the first run (that run fails); after an intended visual change, delete the affected PNGs in `__Snapshots__` (or run with `TEST_RUNNER_SNAPSHOT_TESTING_RECORD=all`), re-run, and look at every new image before committing it.

  Which tests when (test plans in `App/TestPlans`, wired into the scheme by `project.yml`):

  | When | Run | Time |
  |---|---|---|
  | Logic or a screen's layout / looks (models, views, Core) | `-testPlan Unit` (and `cd Core && swift test`): unit, layout and snapshot tests | ~12 s of tests |
  | Gestures, sheet, PDF, navigation, server route; any app PR | `App/TestPlans/console-check.sh <udid>` (Smoke: 4 UI tests + the console) | ~3 min |
  | Before a PR | `-testPlan Full` (unit + 8 UI tests, serial) | see `docs/m2-notes.md` |

  ```sh
  taskpolicy -b xcodebuild test -project App/Ackshually.xcodeproj -scheme Ackshually -destination 'id=<udid>' -testPlan Unit
  taskpolicy -b xcodebuild test -project App/Ackshually.xcodeproj -scheme Ackshually -destination 'id=<udid>' -testPlan Full
  App/TestPlans/console-check.sh <udid>     # Smoke + console; add e.g. -derivedDataPath to reuse a build
  ```
- Architecture diagram: the Claude whiteboard at https://claude.ai/artifact/Wv4rbfpuJmvZqPFjT8nyA1 (linked from spec §5). When a change adds, removes or renames a module, model or service, or changes who depends on what, update the board in the same PR: edit only the boxes and arrows affected, never redraw it. If you can't write to it, say what changed in the PR so the lead updates it.
